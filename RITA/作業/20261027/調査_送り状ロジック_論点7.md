# 調査: 送り状(ヤマト・佐川)のロジック(論点7)

- 作成日: 2026-10-27 / 状態: 調査メモ(コード読解のみ。画面での再現は未確認)
- 出典: DB `TLN_M_GENERAL_ITEM_OPTN`(`SHUKKA_07`)、`TLN_M_HANYO_CODE_MAIN`(共通関数 `RITA_SHK_COMMON`)、`SUB_OKURIJO_RENKEI2`
- 注意: 接続先URL・認証情報・出荷元の住所・電話などは、本メモに書かない。

## 全体像(機能 `SHUKKA_07`)
画面のボタンごとに処理が分かれている。

| ボタン | 処理 |
|---|---|
| 送り状取得(ヤマト) | 同じ出荷日・納入先の梱包をまとめる**複数口**判定あり。外部の送り状API(Ship&Co)を呼び、PDFと送り状Noを保存 |
| 送り状取得(佐川) | 複数口判定なし。1梱包ずつ、佐川として取得 |
| ヤマト手動 / 佐川手動 | 送り状Noを手入力した場合の出荷連携。連携データの送り状Noの先頭に、ボタン名(ヤマト/佐川)を付ける(課題一覧No.9の対応) |
| 出荷連携 | チェックした行を、外部DBの連携テーブルへ登録 |
| 売上のみ / 赤帽 / 引き取り | 別処理(未精査) |

共通関数(`TLN_GENERAL_JAVASCRIPT_ENGINE` / `RITA_SHK_COMMON`、約18KB)に、宛先の組み立て(`buildShipToAddress`)、API呼び出し、区分更新(`updateShukkaKubun`)がある。

## 宛先が異なる/入れ子になる原因の候補
コードから読み取れる、宛先や業者がずれる箇所。**実際の症状の確認前の仮説**。

1. **複数口のまとめ方が粗い(ヤマトのみ)**
   - `getFukusuu` は、出荷日と納入先コードが同じで、`AMOUNT`(口数)があり、非ロットの明細がある梱包を、すべて同じ荷物として束ねる。
   - 運送業者(`UNSO_GYOSYA`)や、実際の宛先住所では、絞り込んでいない。
   - 束ねた全梱包に、クリックした行(代表)の宛先が使われる。同じ納入先コードで宛先が異なる梱包や、佐川向けの梱包が混ざると、宛先や業者が食い違う。
2. **区分(KUBUN)が代表の梱包にしか付かない**
   - `updateShukkaKubun`(ヤマト=2、佐川=4)は、代表の梱包だけに実行される。束ねられた他の梱包は、区分が更新されない。
3. **業者の判定が2系統で食い違う**
   - 連携SQL(`SUB_OKURIJO_RENKEI2`): 送り状Noの先頭で判定する(1111=赤帽、3333=引取、4=ヤマト、5555=売上、5=佐川)。
   - 画面の集計(`SEARCH_AFTER`): 先頭の1〜2桁で判定する(11=赤帽、33=引取、3または4=ヤマト、55=売上、5=佐川)。
   - 「3」始まりがヤマトにも数えられ、「33」始まりの引取と二重に数えられる。「5555」と「5」のように、判定が入れ子になっている。
4. **宛先の住所が、郵便番号に依存する**
   - 郵便番号から都道府県と市区町村を引き(`zipNo`)、住所の文字列からその部分を削除して組み立てる。
   - 郵便番号と住所が一致しないデータでは、住所が欠けたり、別の地域になったりする。

## そのほか、気づいた点(要確認)
- 複数口の処理(`setOkurijjoInfo2`)で、`shukkaRenkei(lineDataMap, service)` の `service` が、その関数内で未定義に見える。実行時にエラーになる可能性がある。
- 宛先のメールアドレスが、固定のダミー値になっている(`buildShipToAddress`)。
- SQLを文字列連結で組み立てている箇所が多い(梱包番号の形式チェックは一部のみ)。

## 必要な情報(症状の特定)
- 「宛先が異なる」の具体例: どの画面・どのボタンで、どの宛先がどうずれるか(伝票PDFの例)。
- 「入れ子」の意味: ヤマトの伝票に佐川の荷物が混ざる、のか。それとも、送り状Noの判定ルールが重なる、のか。
- 期待する動作: 複数口にまとめる単位(納入先コードか、宛先住所か、業者か)。

## 追記: 症状の特定(OBICで、ヤマトなのに佐川と表示される) 2026-10-27
症状: ヤマトで発送したはずの荷物が、OBIC上で「佐川」と記載される。

### 原因(コードとデータからの推定。最有力)
- OBICへ連携するSQL(`SUB_OKURIJO_RENKEI2`)は、**送り状Noの先頭の数字だけで業者名を決めている**。
  先頭が `1111`=赤帽、`3333`=引取、`4`=ヤマト、`5555`=売上のみ、`5`(5555以外)=佐川。
  上記に当てはまらない番号は、業者名が付かない。
- 赤帽・引取・売上のみのボタンは、先頭の数字(1、3、5)が付いた擬似的な番号を登録する(`updateShukkaInfo`)。番号の先頭が、「区分コード」を兼ねている。
- 実際の送り状Noは、外部のAPIが返す番号で、先頭の数字は業者で固定ではない。
  - 例: DB上に、区分が佐川(4)で、番号が「3」始まりの行がある(`SHK_T_SIJI`)。先頭が3のものは、ヤマトの規則(画面集計では3または4=ヤマト)に当てはまる。
  - 逆に、ヤマトの番号が「5」始まりなら、連携SQLでは佐川と書かれる。
- 番号の先頭ではなく、送り状取得時に保存している区分(`SHK_T_SIJI.KUBUN`、ヤマト=2、佐川=4)のほうが、正しい情報を持っている。

### データの状況(参考)
`SHK_T_SIJI` は32行と少なく、区分と番号の先頭の組み合わせは、4通りのみ。ヤマトの実例は1件のみで、「ヤマトの番号が5始まり」の実例は、DBでは確認できていない(OBIC側の連携テーブルは、別のDBにあり、未確認)。

### 改修案
1. `SUB_OKURIJO_RENKEI2` の業者名を、`KUBUN` で決める(2=ヤマト、4=佐川)。`KUBUN` が空の古い行だけ、先頭の数字で判定する。
2. 複数口(ヤマト)の処理で、束ねた**全梱包**に `KUBUN` を設定する(現状は代表の梱包のみ)。これをしないと、1の改修で、同梱の梱包が業者名なしになる。
3. 画面の集計(`SHUKKA_07` の `SEARCH_AFTER`)も、同じ基準にそろえる。
4. 赤帽・引取・売上のみの区分値(`updateShukkaInfo` の中身)を確認し、`KUBUN` との対応を決める。
5. すでにOBICへ誤って連携された分の補正方法を、OBIC側の担当と決める。

### 追加で必要な情報
- ヤマトが佐川と表示された実例の送り状Noの先頭の数字と、連携日(個人情報は不要)。
- OBIC側が、連携テーブルのどの項目(送り状Noの先頭の業者名)を読んでいるか。
- `updateShukkaInfo` の内容と、`KUBUN` の値の一覧。
